## Ambiguities for review

- Classification rule (same as `emit_1`): every test in this file is a TypeScript type test with no `expect`. Tests whose only check is `// @ts-expect-error` (the "should not accept / should reject / should require / should disallow" tests) are N/A-type. Tests that only assert "this compiles" are ported as `assert.NotPanics` around the Go equivalent, because the JS test still executes `setup(...)` / `.createMachine(...)` and would fail if it threw. A reviewer may prefer N/A-type for the positive ones; the Go code compiling is also the Go analogue of the type check.
- JS L363 and L383 are two tests with the identical name; the second Go func gets suffix `2` (`TestSetupTypes_ShouldNotAcceptObjectRefToParameterizedAssignWithoutParams2`).
- Long JS names are shortened in Go func names to stay under ~100 chars; the `// JS:` comment above each func keeps the verbatim name.
- `types: {} as { events / emitted / children / context }` declarations have no runtime effect; they are kept only as Go comments (or as the Go context type `C` for `context`).
- JS L322: `assign((_, params: number) => ({ count: params }))` → `xs.Assign` reading `a.Params.(int)`; entry ref `{ type: 'resetTo', params: 0 }` → `xs.ActionRef{Type: "resetTo", Params: 0}`.
- JS L464: setup has no declared context; the Go assign needs a context type, so a local `ctx{ Child xs.ActorRef }` is used.
- JS L842: `assign({ data: () => ({}) })` on a machine without declared context → local `ctx{ Data any }`, assign sets `Data` to an empty map.
- JS L1219: `input ? Math.min(Math.random(), input) : Math.random()` → `a.Input.(float64)` non-zero check (JS truthiness: `undefined` and `0` are both falsy).
- JS L1256: `createActor(machine).getSnapshot()` on an unstarted actor is expected to expose the invoked child `someChild` (the JS non-null assertion `!` would otherwise throw on `.getSnapshot()`); Go uses `require.NotNil` before reading it.
